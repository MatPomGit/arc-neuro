# ARC-ADHD durable telemetry queue and upload contract

Status: technical data-delivery contract, version 0.1.

This document defines how the mobile application should persist and transmit research telemetry without requiring continuous network connectivity and without creating duplicate analytical events.

## 1. Separation of concerns

The system distinguishes:

1. **scientific event**: immutable research fact generated by the application;
2. **local queue record**: delivery metadata around the immutable event;
3. **upload batch**: transport grouping only;
4. **server acknowledgement**: confirmation that specific immutable event IDs were accepted.

Transport state must not change the scientific meaning of an event.

## 2. Event identity

Each scientific event shall have a globally unique or study-unique stable `event_id`.

The same event retried after network failure must retain the same:

- event_id;
- session_id;
- sequence_number;
- event_type;
- monotonic timestamp;
- scientific payload;
- configuration/version metadata.

A retry must not create a new event ID.

## 3. Session sequence

Every event in one session receives a monotonically increasing integer `sequence_number`.

Purpose:

- reconstruct local ordering;
- detect missing events;
- detect duplicate/rewritten ordering;
- support deterministic replay.

Sequence number is independent of wall-clock time.

## 4. Scientific timestamp

Use:

- monotonic milliseconds from session start for scientific timing;
- optional coarse wall-clock metadata only when operationally required.

The monotonic clock is authoritative for within-session ordering.

## 5. Event envelope

Required event-envelope fields:

- event_schema_version;
- event_id;
- participant_pseudonym;
- session_id;
- sequence_number;
- event_type;
- monotonic_ms;
- intervention_version;
- configuration_hash;
- payload.

The event payload is event-type specific.

The envelope must not contain direct participant identity.

## 6. Local queue record

A queue record wraps one immutable event with delivery metadata.

Required transport fields:

- queue_schema_version;
- delivery_state;
- attempt_count;
- event.

Optional transport fields:

- last_attempt_wallclock;
- acknowledgement_id;
- acknowledged_wallclock;
- last_transport_error.

Transport metadata is not part of scientific analysis by default.

## 7. Delivery states

Minimum states:

### pending

Event is durably stored locally and has not been acknowledged.

### in_flight

Optional transient state while an upload request is active.

If the process dies in this state, it returns to pending on recovery unless acknowledgement can be proven.

### acknowledged

Server explicitly confirmed the exact `event_id`.

Only acknowledged records may become eligible for local cleanup according to retention policy.

### blocked

Optional state for a record that cannot be uploaded because local validation failed or configuration integrity is broken.

Blocked records must not be silently discarded.

## 8. Durable write ordering

For a new scientific event:

1. construct event;
2. validate required structure;
3. assign event ID and sequence number;
4. durably persist local queue record;
5. only then report successful event commit to scientific state logic;
6. attempt upload later/asynchronously.

A scientific transition that depends on successful event persistence must not advance before step 4 succeeds.

## 9. Upload batching

Batches are transport units only.

A batch may contain multiple event records from one or more sessions if allowed by the backend, but each event retains its own stable identity.

Recommended batch fields:

- batch_id;
- client_app_version;
- event IDs;
- events;
- optional batch checksum.

Batch retry may reuse the same batch ID or construct a new batch containing the same event IDs. Server idempotency is event-based.

## 10. Server idempotency

The research backend shall treat `event_id` as an idempotency key.

Required behavior:

- first valid event ID + payload: accept;
- identical retry: acknowledge without adding a duplicate analytical event;
- same event ID with different scientific payload: reject as an integrity conflict;
- malformed event: reject with event-specific error;
- partial batch acceptance: return per-event result.

Do not deduplicate only by timestamp because distinct events can share timestamps.

## 11. Acknowledgement

Server response should identify at least:

- accepted event IDs;
- already-known identical event IDs;
- rejected event IDs and reason.

The client marks an event acknowledged only when its ID appears in accepted/already-known confirmation.

A successful HTTP status without per-event acknowledgement is not sufficient for destructive local cleanup.

## 12. Cleanup

Normal cleanup rule:

- acknowledged;
- acknowledgement durably persisted;
- retention policy allows deletion.

Never delete pending/blocked events merely to reduce queue size without a separately documented emergency policy.

## 13. Crash recovery

At application start:

1. load queue;
2. validate queue records;
3. return stale in-flight records to pending unless acknowledgement is known;
4. preserve original event ID and payload;
5. continue retry under bounded backoff.

A crash must not regenerate already committed event IDs.

## 14. Ordering on the server

Analysis ordering within a session uses:

1. sequence_number for event order;
2. monotonic_ms as scientific timing;
3. event_id for uniqueness.

Upload arrival order is not scientific order.

## 15. Integrity conflict

An integrity conflict occurs if the same event ID appears with different immutable scientific content.

Required behavior:

- do not silently choose one version;
- retain conflict record;
- mark session/data quality issue;
- prevent deterministic replay from treating the conflict as valid.

## 16. Queue capacity

The application should estimate whether sufficient local storage exists before starting a participant session.

If required durable capacity cannot be guaranteed, the research session should not start or should enter a defined protocol abort.

Queue capacity must not trigger deletion of unacknowledged scientific events.

## 17. Network independence

Network availability shall not determine:

- cognitive difficulty;
- challenge eligibility;
- recovery score;
- safety behavior;
- child stop/pause;
- state-machine transitions except post-session upload UI.

## 18. Privacy

Queue records contain pseudonymous research data only.

Forbidden direct identifiers include:

- participant name;
- caregiver name;
- email;
- phone number;
- postal address;
- IP address stored as scientific payload;
- precise GPS coordinates.

Backend transport infrastructure may observe networking metadata operationally, but these are not research telemetry fields by default.

## 19. Error taxonomy

Suggested transport error categories:

- network_unavailable;
- timeout;
- server_unavailable;
- authentication_failure;
- payload_rejected;
- schema_mismatch;
- integrity_conflict;
- local_storage_failure;
- unknown_transport_error.

Transport errors must not be confused with participant/task missingness codes.

## 20. Analysis export

The analysis dataset should be built from acknowledged immutable scientific events, not from delivery-attempt rows.

Transport logs may be retained separately for data-quality auditing.

## 21. Machine-readable contract

The local queue record schema is:

`schemas/telemetry_queue_record.schema.json`.

Synthetic fixtures are stored under `examples/`.

The schema validates transport/event structure. Event-specific scientific payload validation remains the responsibility of its corresponding event contract.
