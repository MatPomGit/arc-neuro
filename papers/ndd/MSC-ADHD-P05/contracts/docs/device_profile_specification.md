# ARC-ADHD BYOD device qualification specification

Status: Phase 0 device-compatibility specification, version 0.2.

ARC-ADHD Phase 0 is designed for **bring your own device (BYOD)** use. The child/caregiver uses a private Android phone rather than a standardized research handset.

The scientific consequence is that the study cannot assume identical timing, refresh behavior, audio, haptics, storage, thermal performance or operating-system behavior across participants. Device heterogeneity must therefore be measured, bounded and included in feasibility assessment.

## 1. Core principle

The study freezes **device-qualification rules**, not one phone model.

Every installation or materially changed device configuration must pass an in-app qualification procedure before a participant-facing research session can begin.

A device that lacks an optional capability may still qualify for the core study when a defined fallback exists.

## 2. Private-device boundary

The application runs on a phone owned or routinely used by the participant/caregiver.

The application shall not require:

- a dedicated research phone;
- removal of the user's personal account;
- access to contacts;
- access to SMS or call history;
- access to photos/media unrelated to the study;
- advertising ID;
- hardware serial number;
- IMEI;
- Android ID as a research identifier;
- precise geolocation;
- microphone access for the core intervention;
- camera access for the core intervention.

The research identity remains the pseudonymous study ID.

## 3. Qualification model

Qualification has three outcomes:

- **qualified_core**: all mandatory core checks pass;
- **qualified_with_fallbacks**: core checks pass but one or more optional capabilities are disabled;
- **not_qualified**: a mandatory requirement fails.

The qualification result is recorded before the session begins.

## 4. Mandatory core checks

The private phone must support:

- compatible Android/application runtime;
- reliable capacitive touch input;
- readable child-facing UI at current display/scaling settings;
- monotonic timing source;
- durable app-local storage;
- sufficient free app storage for one complete session plus retry queue;
- offline execution for the complete core session;
- acceptable benchmark performance for the configured task;
- reliable pause/stop controls;
- stable application lifecycle during the qualification run.

Camera, microphone, AR and haptics are not mandatory.

## 5. Qualification timing

Qualification should run:

- after first installation;
- after an application update that changes timing/task/runtime behavior;
- after an operating-system update when detectable;
- when the device capability fingerprint changes materially;
- after repeated runtime/timing failure;
- when the researcher explicitly requests requalification.

A short pre-session health check still runs before every session.

## 6. Device capability profile

The application may record a privacy-minimized capability profile such as:

- platform;
- Android major version;
- application/runtime version;
- display refresh-rate bucket;
- logical screen-size bucket;
- touch available;
- ordinary audio available;
- haptic available;
- local storage test result;
- benchmark class;
- background/resume test result;
- thermal-warning state if exposed by the platform;
- battery/power-saving warning state;
- qualification version.

The default research export should avoid exact model identifiers unless a later analysis plan demonstrates that they are necessary and proportionate.

## 7. Installation identifier

To detect a change of device/profile across sessions, the app may generate a random app-local installation identifier.

Requirements:

- generated by the ARC-ADHD app;
- not derived from IMEI, serial number, Android ID, account, advertising ID or MAC address;
- pseudonymous;
- scoped to the research app;
- resettable on app-data deletion/uninstall;
- not used for cross-app tracking.

The study participant ID remains separate.

## 8. Capability fingerprint

A capability fingerprint may be computed from coarse research-relevant capabilities and version fields.

It must not be designed as a unique commercial device fingerprint.

Purpose:

- detect meaningful changes in the execution environment;
- decide whether requalification is required;
- support sensitivity analysis of device heterogeneity.

## 9. Display variability

The app must adapt layout to varying:

- screen size;
- aspect ratio;
- pixel density;
- system font scaling;
- safe areas/cutouts;
- refresh rate.

Scientific task geometry should be specified in normalized/logical units where possible.

UI acceptance checks must ensure:

- stop/pause remains visible;
- targets meet configured minimum logical size;
- no critical content is clipped;
- child-facing text remains readable.

## 10. Timing variability

BYOD means raw mobile reaction time contains device-dependent latency.

Therefore:

- within-session event timing uses a monotonic clock;
- the app records a coarse timing/performance profile;
- recovery analysis should prioritize within-person change on a stable device/profile;
- switching phones or materially changing the execution profile is a protocol-relevant event;
- confirmatory clinical conclusions must not depend solely on raw millisecond in-game RT;
- device/profile sensitivity analyses should be prespecified when RT contributes materially to a derived endpoint.

If device/profile changes between sessions, RT-dependent reference values may require reset or explicit stratification rather than silent continuity.

## 11. Local performance benchmark

The cross-device engineering procedure is specified in `docs/byod_cross_device_benchmark_protocol.md`.

The qualification procedure should include a short deterministic benchmark using the same runtime path as the task.

The benchmark should assess:

- frame-time stability;
- dropped/stalled frames;
- task event scheduling;
- local storage write/read;
- monotonic sequence integrity;
- state-machine transitions;
- telemetry queue persistence;
- background/resume handling.

The benchmark produces a **qualification result**, not a hardware prestige score.

## 12. Thermal and power variability

Private phones may enter thermal throttling or battery-saving modes.

Before and during a session, where platform APIs permit, the app should detect or warn about conditions likely to alter performance.

The application should:

- warn before starting if available battery is clearly insufficient;
- record relevant power-saving/thermal warnings;
- pause/abort when device behavior makes scientific timing unreliable;
- never disable user safety protections to preserve the study.

## 13. Notifications and interruptions

Because the phone remains a personal device, incoming notifications, calls and app switches are expected risks.

The app should:

- recommend a low-interruption mode before session start;
- not silently change system-wide user settings without consent;
- record application focus loss/backgrounding;
- treat interruptions according to the state-machine validity rules;
- invalidate a recovery event when the interruption destroys its interpretability;
- allow safe resume when validity is preserved.

## 14. Audio

Ordinary audio is optional for the core.

Qualification records:

- whether audio output is available;
- whether required functional sound can be played;
- whether the study uses visual fallback.

The application must not inspect unrelated media/audio history.

Headphones are not required for the core.

## 15. Haptics

Haptics are optional.

Qualification records:

- capability available/unavailable;
- whether the configured test pattern can be invoked;
- fallback availability.

A phone without haptics may qualify for the core condition when haptics are not required by that condition.

## 16. Storage and app data

Research data are written only to application-controlled storage.

The app must not require broad storage/media permissions for core telemetry.

Before a session:

- verify writable storage;
- verify sufficient queue capacity;
- verify previous unacknowledged data remain recoverable.

If durable storage cannot be guaranteed, the device is not currently qualified for a participant-facing session.

## 17. Offline-first use

A qualified device must complete the core session without continuous internet access.

Network availability affects upload only, not:

- task difficulty;
- challenge eligibility;
- safety behavior;
- recovery computation;
- strategy selection;
- session timing.

## 18. Device changes across sessions

When a participant uses a different private phone or materially changed capability profile:

1. run full qualification;
2. assign/update the installation/capability profile;
3. log the profile change;
4. do not assume RT/reference comparability automatically;
5. apply the prespecified reference-reset/sensitivity rule.

Device switching must not silently merge timing-sensitive data.

## 19. Digital-exclusion monitoring

BYOD eligibility is a feasibility outcome.

Phase 0 should report:

- proportion of screened private phones that qualify;
- proportion qualifying only with fallbacks;
- reasons for non-qualification;
- Android-version distribution in coarse form;
- optional capability availability;
- frequency of device/profile changes;
- technical interruption rate by capability/performance class.

If qualification requirements exclude a substantial subgroup, the application requirements should be reconsidered before efficacy testing.

## 20. Privacy minimization

Do not collect a field merely because Android exposes it.

Default research telemetry should not contain:

- device serial;
- IMEI;
- phone number;
- SIM information;
- account identifiers;
- Wi-Fi SSID/BSSID;
- MAC address;
- advertising ID;
- installed-app list;
- contact list;
- precise GPS;
- personal filenames or media metadata.

## 21. Phase 0 compatibility support policy

Before recruitment, define a versioned compatibility policy containing:

- minimum supported Android/API range;
- excluded runtime configurations, if any;
- mandatory core capabilities;
- benchmark acceptance rules;
- fallback rules;
- requalification triggers.

These are frozen study rules even though the physical phone model is not.

## 22. Machine-readable template

The machine-readable template remains:

`config/device_profile.phase0.template.json`.

It now describes a **private-device qualification/capability profile**, not a standardized study handset.

Model/manufacturer are not required in the default frozen scientific profile.
